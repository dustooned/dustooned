# Journal System

Journal posts are MDX files in `src/content/journal/`.

Required fields:

- `title`
- `date`
- `excerpt`

Optional fields:

- `thumbnail`
- `image`
- `tags`
- `featured`

Use `RawPostInsert.astro` for intentionally custom inserted blocks.

Do not execute arbitrary external scripts by default. Iframes and embeds should be reviewed before publishing.

## Thumbnails vs. hero image

Two separate fields cover two separate jobs — do not conflate them:

- **`thumbnail`** — small, cropped `thumb.webp` used only in grid cards (`/journal` list and
  any other place a `JournalCard` renders). Generated by
  `node scripts/generate-smart-thumbnails.mjs` from an `image-1.*` source file in the post's
  `public/images/journal/{slug}/` folder — see `docs/ASSET_GUIDE.md` for the generator.
- **`image`** — the post hero shown at the top of the post itself in `JournalLayout.astro`.
  For static (non-gif) sources this is the full original source file, unresized/uncropped.
  For gif sources it is **not** the raw original — see the gotcha below for why. The
  generator writes this automatically alongside `thumbnail`; you don't need to set it by
  hand for posts backed by a local image. `JournalLayout` falls back to `thumbnail` if
  `image` isn't set (e.g. video-only posts, see below).

Regenerating via the script keeps both in sync; don't hand-edit `thumbnail` without also
checking `image` still points at the right source.

### Gotcha: GIF thumbnails AND hero images must stay animated, but small

GIF-sourced thumbnails are generated at a much smaller size than static ones (640x480 vs.
1600x1200, lower quality) specifically because animated webp cost scales with pixel count
per frame — the original 1600x1200 animated thumbnails were multi-megabyte files that visibly
lagged the `/journal` grid. See `docs/ASSET_GUIDE.md` for the exact dimensions/quality
constants.

The same is true of the post hero (`image`), and it's easy to get this wrong: a raw GIF
"only loads once per post view", but decode/repaint cost is paid continuously for as long as
the animation is on screen, not just once — a full-resolution, 25-85-frame GIF squeezed down
to ~480px via CSS caused visible scroll jank on the post page even though it only downloaded
once. The generator re-encodes gif sources to a resized (640px cap), lower-quality animated
webp and uses **whichever file (webp or original gif) is smaller** — some flat-color/line-art
GIFs compress better as GIF than as animated webp at the same resolution, so this isn't a
blind "always convert" rule. Any additional gifs referenced directly in a `<MediaGallery>`
in the MDX body (not just the post's main `image-1`) get the same treatment, with the MDX
file's image array rewritten in place to point at the optimized version. See
`docs/ASSET_GUIDE.md` for the implementation.

For posts whose content *is* a video embed (`RawPostInsert` + YouTube iframe) rather than a
local image, `thumbnail` can instead point straight at the YouTube thumbnail, same convention
as Motion — no `image` field needed, no local asset generated:

```yaml
thumbnail: "https://img.youtube.com/vi/{videoId}/hqdefault.jpg"
```

`withBase()` passes absolute `https://` URLs through unchanged.
